5개 문서를 모두 읽었습니다. 전체적으로 게임의 **비전과 방향**은 명확하지만, 실제 개발을 시작하기에는 **구체적 규칙과 시스템 설계**가 많이 부족합니다. 아래에 문서별로 보완이 필요한 부분과 궁금한 점을 정리합니다.

---

## 📋 문서별 피드백

### 1. Target Outcome.md — 방향은 좋으나 핵심 루프 정의 부족

**보완 필요:**
- "카드를 사용해야 기물을 움직일 수 있다"는 핵심 제약이 있는데, 이것만으로는 **한 턴의 흐름(Turn Flow)**이 그려지지 않습니다.
- **핵심 루프 예시**가 필요합니다: `드로우 → 카드 선택 → 기물 선택 → 이동/효과 적용 → 턴 종료` 같은 단계별 흐름.

**궁금한 점:**
- 🔸 **"지휘관"의 역할은 무엇인가요?** 플레이어가 보드 위의 특정 기물(킹 등)인가요, 아니면 보드 밖에서 모든 기물을 조종하는 추상적 존재인가요?
- 🔸 **로그라이크의 "런(Run)" 구조**는 어떤가요? `전투 → 보상(카드 획득) → 맵 선택 → 전투 ...` 이런 Slay the Spire 식 구조인가요?
- 🔸 **패배 조건**은 무엇인가요? 킹이 잡히면? 모든 기물이 전멸하면? 체력 시스템이 있나요?

---

### 2. Rulebook.md — 범용 아키텍처 규칙이며, 게임 규칙이 아님

이 문서는 **Godot 엔진 코딩 규칙**(user_rules와 동일)이지, 체스+덱빌딩 게임의 **게임 규칙서(Rulebook)**가 아닙니다.

**보완 필요 — 실제 게임 규칙서 작성:**
- 🔸 **보드 구성**: 몇 x 몇 보드인가요? 표준 체스 8×8인가요?
- 🔸 **초기 배치**: 표준 체스 배치를 따르나요? 기물 종류는 동일한가요(폰, 룩, 나이트 등)?
- 🔸 **카드 사용 규칙**:
  - 턴당 카드를 몇 장 쓸 수 있나요?
  - 카드를 써야만 기물이 움직이나요? (예: "폰 전진" 카드가 있어야 폰을 움직이는 식?)
  - 카드 비용(마나/AP 등) 시스템이 있나요?
  - 핸드 사이즈 제한은?
  - 턴 시작 시 드로우 수는?
- 🔸 **기물 잡기(Capture)**: 체스처럼 이동으로 잡나요? 잡은 기물은 어떻게 되나요?
- 🔸 **특수 카드의 예시**: "기존 체스와는 다른 방식"이라고 했는데, 어떤 종류의 특수 효과를 구상 중인가요?
  - 예: 기물 변환, 추가 이동, 보드 지형 변경, 기물 소환, 버프/디버프 등

---

### 3. ARCHITECTURE.md — 골격만 있고 살이 없음

**보완 필요:**
- **Entity**가 구체적으로 무엇인가요? 보드 위의 기물(Piece)인가요? 플레이어도 Entity인가요?
- **Card Data / Card Effect** 분리는 좋은데, Card Data에 어떤 필드가 들어가는지 정의가 필요합니다.
  - 예: `card_name`, `cost`, `card_type(이동/공격/특수)`, `target_piece_type`, `effect_script` 등
- **Board Manager**의 역할 범위: 보드 상태 관리만? UI 렌더링도 포함?
- **빠진 시스템들:**
  - `Deck Manager` (덱/핸드/묘지 관리) — Card Manager와 별도인지?
  - `Roguelike Manager` (맵 진행, 보상, 이벤트 관리)
  - `UI Manager` (카드 핸드 UI, 보드 UI, 메뉴 등)
  - `Save/Load System`

---

### 4. FEATURES.md — 항목 나열 수준, 우선순위와 상세 부족

**보완 필요:**
- 각 피처에 **우선순위(MVP / Post-MVP)**를 매겨야 합니다.
- "카드 획득 / 사용 / 제거"만으로는 부족합니다:
  - 🔸 **덱 구성 시점**: 전투 전? 전투 중에도 가능?
  - 🔸 **카드 종류 분류 체계**: 이동 카드 / 공격 카드 / 특수 카드 정도의 큰 분류가 필요
- 로그라이크 시스템의 "이벤트"와 "상점"은 어떤 내용인가요?

---

### 5. TASKS.md — 너무 높은 레벨의 태스크

**보완 필요:**
- "보드 생성"이 하나의 태스크로는 너무 큽니다. 하위 태스크 분해가 필요합니다.
  - 예: `보드 데이터 구조 설계 → 보드 시각화(타일 렌더링) → 기물 배치 로직 → 기물 시각화`
- 카드 시스템 관련 태스크가 "카드 사용" 하나뿐인데, 덱빌딩 게임에서 카드 시스템은 최소:
  - `카드 데이터 리소스 설계 → 카드 UI → 핸드 관리 → 카드 효과 시스템 → 덱 관리`

## 🎯 개발 시작 전 반드시 답해야 할 핵심 질문 요약

| # | 질문 | 이유 |
|---|------|------|
| 1 | **한 턴의 정확한 흐름은?** | 이것이 확정되지 않으면 Turn Manager, Card Manager, Board Manager 모두 설계 불가 |
| 2 | **카드와 기물 이동의 관계는?** | "이동 카드" 1장 = 기물 1회 이동? 카드 종류별로 이동 가능한 기물이 정해져 있나? |
| 3 | **카드 비용 체계(마나/AP)가 있는가?** | 턴당 행동 제한의 핵심 메커니즘 |
| 4 | **승리/패배 조건은?** | 킹 체크메이트? 기물 전멸? HP 시스템? |
| 5 | **보드 규격과 초기 배치는?** | 표준 체스 vs 커스텀 보드 — 데이터 구조 설계에 직접 영향 |
| 6 | **특수 카드의 구체적 예시 3~5개** | 이 게임만의 차별점을 코드로 구현하려면 효과 시스템 설계가 필요 |
| 7 | **로그라이크 런 구조(메타 루프)는?** | 전투 사이의 흐름이 정해져야 Roguelike Manager를 설계 가능 |

---

이 질문들에 대한 답변을 주시면, 그것을 바탕으로 **게임 규칙서 보완 → 아키텍처 상세 설계 → 구현 계획** 순서로 진행하겠습니다. 어디부터 답변해 주셔도 좋습니다.
